# Окна событий на Go

[![Я проверяю проект](https://github.com/Decl1s/go-event-windows/actions/workflows/check.yml/badge.svg)](https://github.com/Decl1s/go-event-windows/actions/workflows/check.yml)

Я считаю продажи магазинов по пятиминутным окнам **времени события** и показываю,
почему опоздавшее сообщение иногда уже нельзя включить в опубликованный итог.
Я обрабатываю дубли, отделяю поздние события, сохраняю трассу watermark и честно
помечаю незакрытый хвост `eof_preview`. Это учебная лаборатория на синтетических
данных, которую я показываю за 5–10 минут. Сервер, Kafka и облако мне не нужны.

## Как я запускаю

Я использую Go **1.27.3**. Сторонних Go-модулей нет. Для полного gate и исходного
ZIP дополнительно нужен Python **3.14.4**; для самого CLI Python не нужен.
Я устанавливаю Go с [официального сайта](https://go.dev/dl/), затем открываю
терминал в корне проекта. Все следующие команды работают и в PowerShell.
`go.mod` требует эту версию; более старый Go с включённым auto toolchain может
скачать её. Я не меняю глобальные настройки Go.

```text
mkdir artifacts
go run ./cmd/windowlab demo -out artifacts/events.jsonl
go run ./cmd/windowlab run -in artifacts/events.jsonl -out artifacts/report.json
```

Я открываю `artifacts/report.json` в редакторе. Я ожидаю:

| Счётчик | Значение |
| --- | ---: |
| Строки | 11 |
| Принятые уникальные события | 6 |
| Повторные события | 2 |
| Поздние события | 2 |
| Неправильные строки | 1 |
| Группы (окно, магазин) | 4 |
| Итоговая сумма, копейки | 83 000 |

Я получаю три окна `watermarked` и одно `eof_preview`:

| Начало UTC | Магазин | Число | Копейки | Статус |
| --- | --- | ---: | ---: | --- |
| 10:00 | NORTH | 2 | 30 000 | watermarked |
| 10:00 | SOUTH | 1 | 7 000 | watermarked |
| 10:05 | NORTH | 2 | 35 000 | watermarked |
| 10:10 | SOUTH | 1 | 11 000 | eof_preview |

Я читаю `trace`: watermark проходит 09:59 → 10:02 → 10:06 → 10:10 UTC.
Я сохраняю пропуски в `rejections`: строки 6 и 10 — `window_closed`, строка 8 —
`invalid_value`. Я не копирую исходную ошибочную строку в отчёт.

## Как я меняю результат

```text
go run ./cmd/windowlab run -in artifacts/events.jsonl -out artifacts/lag10.json -lag 10m
go run ./cmd/windowlab run -in artifacts/events.jsonl -out artifacts/repeat.json
```

При `lag 10m` я принимаю 8 событий и получаю 98 000 копеек без опозданий.
`repeat.json` побайтово совпадает с исходным `report.json`. Если я повторю команду
с уже занятым `-out`, CLI откажет и сохранит прежний файл. Для нового опыта я
выбираю другое имя. Я не сортирую вход: порядок строк — часть эксперимента.

## Мой контракт

```json
{"event_id":"e1","store":"NORTH","occurred_at":"2026-10-29T10:01:00Z","amount_minor":10000}
```

Я принимаю ровно четыре поля без повторных ключей: ID из 1–40 латинских букв,
цифр, `_`, `-`; store по `[A-Z][A-Z0-9_-]{0,15}`; существующую UTC дату 2020–2099
в точности до секунды с `Z`; целое `amount_minor` от 1 до 10¹² копеек. Я не
принимаю `null`, дроби, экспоненту, неизвестные поля и смещение вместо `Z`.
В одной лабораторной серии я считаю валюту общей, возвраты не моделирую.
Один ID с другим содержимым останавливает весь запуск. Точный дубль уже позднего
события я считаю дублем; первое опоздание остаётся в журнале.

Окно — `[start, end)`. Я вычисляю `watermark = max(принятое event time) − lag`.
До добавления новой строки я проверяю `end <= предыдущий watermark`: такое окно
уже закрыто. Время самого процесса на результат не влияет. Некорректная строка
и дубль watermark не двигают. В конце файла я не двигаю его до бесконечности.
`eof_preview` означает, что я закончил читать файл, а закрытие окна не доказал.

## Все параметры

| Флаг | По умолчанию | Зачем я его ввёл |
| --- | --- | --- |
| `-in` | обязательный для run | Файл прибытия JSONL |
| `-out` | обязательный | Только новый файл, без замены |
| `-window` | `5m` | От 1s до 1h, целые секунды и делитель суток |
| `-lag` | `2m` | Допустимое отставание watermark, 0s–24h |
| `-max-rows` | 100000 | Все строки; диапазон 1–1000000 |
| `-max-groups` | 10000 | Все пары окно/магазин; диапазон 1–100000 |

Я ограничиваю строку буфером 64 KiB, все ID/трассу/результаты — лимитом строк,
все группы — отдельным лимитом. Я не обещаю постоянную память: дедупликация и
учебная трасса растут до заданных ограничений. При ошибке чтения, конфликте,
превышении лимита или отсутствии принятых событий я не создаю отчёт.

## Как я проверяю и собираю

```text
go test ./...
go vet ./...
python scripts/ci.py
go build -trimpath -o artifacts/windowlab ./cmd/windowlab
python scripts/package_release.py
```

На Linux я дополнительно запускаю `python scripts/ci.py --race`. На Windows
для ручной сборки я использую `-o artifacts/windowlab.exe`. CLI возвращает
0 при успешной записи, 1 при ошибке данных/файлов, 2 при неверных аргументах.
`go run` может обернуть ненулевой код своей ошибкой; точные коды я проверяю у
собранного приложения. Неправильные отдельные строки я учитываю в отчёте, поэтому
успех команды сам по себе не означает отсутствие брака.

В `dist/` я собираю source ZIP и SHA256SUMS по `PUBLIC_FILES.txt`. В GitHub Actions
я выполняю gate на Linux и Windows; релиз разрешаю только после обеих ОС для
push в main. Фактические результаты читаю в [VALIDATION](VALIDATION.md) и Actions.

## Границы моего решения

Я воспроизвожу конечный файл с одним глобальным watermark. Я не реализовал
checkpoint/resume, retraction, таймеры простоя, несколько партиций, брокер и
exactly-once между процессами. Корректная по контракту далёкая дата способна
сдвинуть watermark: для настоящего источника я добавил бы отдельную проверку
часов. Watermark здесь — моё выбранное правило, а не гарантия полноты бизнеса.
Я не проверял нагрузку, power loss или враждебную конкуренцию за выходной путь.
